## 2026-09-19 제품 목적 보완 — AI 간 작업 인계와 사용자 개입

사용자 확인: CODAST의 목표는 설계 자료를 투입하고 서로 다른 AI 에이전트·모델에 설계→개발→테스트 케이스 설계→E2E를 맡기며 산출물과 작업을 연결하는 개인용 로컬 오케스트레이션이다. 사람이 매번 결과를 기다리고 해석해 다음 지시서를 만드는 부담을 줄인다. 세션 관리·데이터 가드는 이를 받치는 구현 기반이다.

합의된 범위에서는 AI가 자율 진행하고, 정보 부족·중요 결정·가드 위반 등에서는 알림·질문·승인 대기·차단을 구분한다. 사용자 결정 후에는 적용 범위를 기록하고 관련 단계부터 재개하는 것이 목표다. 아래 기존 기반 작업의 완료 상태나 구현 순서를 이 목적 보완만으로 변경하지 않는다. 상세 목표와 평가 기준은 [README](../README.md)를 따른다.

- [ ] 단계별 에이전트·모델·입력·산출물·완료 조건을 정의하고 인계할 버전과 근거를 연결한다.
- [ ] 단계 진행·사용자 개입·중단·재개의 상태와 의존 관계를 정의한다. 알림을 승인으로, 응답 부재를 동의로 취급하지 않는다.
- [ ] 검증 실패의 근거를 담당 단계로 전달하고 허용 범위·재시도 한도 안에서 수정·재검증한다. 기존 실패 실행을 무조건 자동 재시도하는 변경과 구분한다.
- [ ] 수동 인계와 비교해 사람의 시간·개입 누락·불필요한 중단·재작업·품질·총 시간·토큰 비용을 평가한다.

2026-09-19 설계 근거 보완: 현재는 목표 구조를 구체화하고 검증하는 초기 단계다. 시각화와 보고서 생성은 선택 기능이며 작업 인계와 검증, 사용자 개입과 재개가 핵심이다. 공식 레퍼런스와 적용 이유, 대안, 평가 조건은 [설계 근거](orchestration-design.md)에 정리했다. 아래는 후속 검증 범위이며 기존 기반 작업의 순서를 변경하지 않는다.

- [ ] 작은 기능 하나로 설계부터 구현, 테스트, 제한된 수정까지 연결하는 흐름을 검증한다. 담당 모델은 명시적으로 지정한다.
- [ ] 사용자 판단 대기와 답변 반영, 서버 재시작, 오래된 산출물과 승인 범위 변경을 포함한 재개 조건을 검증한다.
- [ ] 단계 검증을 해당 코드와 입력 버전에 연결하고 에이전트 정상 종료와 완료 조건 충족을 구분한다.
- [ ] 단일 에이전트, 수동 인계, CODAST 자동 인계를 같은 조건에서 비교하고 반복 실행의 편차와 추가 비용을 기록한다.

## 1. 제품 목적과 화면 기준

### 2026-09-19 인수인계 — 다음 세션의 우선순위

사용자 결정 당시에는 아래 요구를 TODO로 기록하고 구현을 후속 세션으로 넘겼다. **세션 안정화의 남은 작업 → 업로드 정제 → 자료 연결·재사용 → 시각 설계** 순서가 이전 구현 순서보다 우선한다. 2026-09-19 후속 요청으로 첨부 가드 1차 구현을 진행했으며 현재 범위는 [첨부 가드 계약](data-guard.md)을 따른다. 유료 서비스는 도입하지 않았다.

- [ ] 다음 세션에서 Git 상태·현재 구현 계약·관련 코드와 검증 기록을 확인하여 완료/미완료를 대조한다. 고유 채팅 ID, 재전송 중복 방지, 종료 알림, 명시적 질문 저장·답변 재개는 이미 구현된 기반으로 취급하고 근거 없이 다시 만들지 않는다.
- [x] 격리된 가짜 데이터로 SQLite 백업·복원 후 채팅·실행·질문·네이티브 연결의 보존을 검증했다. WAL 반영, 질문 답변 재개·중복 방지, 실행 중 기록의 자동 재실행 방지를 확인했다. 외부 CLI 세션의 실제 유효성은 별도 미검증이다. [검증 범위](client-runtime.md#db-백업복원-검증--2026-09-19).
- [x] 채팅 복원의 설정·워크스페이스·채팅 목록·대화·실행·질문·룰북 조회 실패/지연 중 초안과 선택 보존, 새로고침 재시도, 이전 응답 무시를 보완했다. Codex·Claude 공통 경로와 브라우저 검증 완료. 자료 탐색 UI는 폐기된 상태를 유지한다. [현재 계약](client-runtime.md#조회-실패-중-채팅-작성-상태-보존--2026-09-19).
- [x] 원본 Codex CLI의 `exec resume` 직접 재개 → 하네스 복귀, DB 백업·복원 후 실제 네이티브 세션 재개와 요청 중복 방지를 검증했다. 실제 모델 요청 4회, 관련 자동 검사 16개 통과. [검증 범위](validation-resume-gaps-2026-09-19.md).

세부 후속 요구는 아래 **2026-09-19 후속 코어 기능**에 모았다. 과거 UI 계획은 최신 구현 계약과 대조하며 폐기된 문서 탐색/편집 UI를 되살리지 않는다.

이 단계의 기반 구현 목적은 **에이전트 네이티브 세션과 채팅 세션을 관리하고 작업을 이어가는 것**이다. 제품 전체 목표는 위의 AI 간 작업 인계와 사용자 개입 절을 따른다. 생산성은 완료 시간·사람 개입·재작업·성공률·토큰 사용량으로 평가한다. 요구사항·산출물 관리가 세션 관리보다 먼저 커지지 않도록 한다.

- [x] 사용자와 기본 정보 배치 합의: 접이식 왼쪽 메뉴, 낮은 높이의 상단 요약 3칸, 중앙 작업 대화, 하단 에이전트·모델 선택과 입력.
- [x] [작업실 데모](../app/web/static/session-demo.html)와 [상세 사용량 데모](../app/web/static/session-metrics-demo.html) 작성. 예시 데이터이며 실제 실행·설정 저장 없음.
- [ ] 데모 배치를 실제 작업실에 적용한다. 현재 `/`의 세션 UI는 이전 단계 구현이며 최신 데모 배치와 다르다.
- [ ] 상단 왼쪽: AI·세션·상태·컨텍스트 사용률·누적 토큰·실제 모델을 간결한 행으로 표시한다. 기본 4행과 내부 스크롤은 제안 상태이며 실제 배치 검토 후 확정한다. 표시 행 수와 동시 실행 한도는 별개다.
- [ ] 상단 가운데: 계정의 시간별·주간 한도 및 초기화 정보를 요약한다. 제공된 제한 창을 사용하고 임의로 주간 한도라고 표시하지 않는다.
- [ ] 상단 오른쪽: 선택 프로젝트와 연결된 Git·개발 서버 포트·Docker 정보를 요약한다. 관련 없는 머신 전체 정보를 나열하지 않는다.
- [ ] 상세 토큰·사용 내역은 별도 대시보드로 이동한다. 메인 영역을 펼쳐 세로로 커지게 만들지 않는다. 최근 채팅은 에이전트별 3개·마지막 실행 순·완료 포함 기준을 재사용한다.
- [ ] 왼쪽 메뉴의 프로젝트·채팅, 룰북·참고 자료, 에이전트 연결·실행 설정, 문서·기록·사용량 화면을 기존 기능과 연결한다.

완료 기준: 합의된 화면에 실제 데이터를 연결하고, 미지원·미수신·조회 실패를 구분한다. 기본 화면에서 상태 요약과 메시지 입력이 함께 보인다.

## 3. 코어 — 채팅과 네이티브 세션 관리

SQLite v8의 고유 채팅 ID로 대화와 클라이언트·작업 경로·권한별 네이티브 세션을 연결한다. 이름 변경과 서버 재시작 뒤에도 ID와 연결을 유지하며 Codex·Claude에 같은 경로를 적용한다. [저장 코드](../app/core/storage.py)와 [실행 코드](../app/core/orchestrator.py)를 기준으로 필요한 부분만 확장한다.

- [x] 고유 채팅 ID와 고정·보관을 SQLite에 저장한다. 기존 데이터 이전, 이름 변경·이름 재사용·서버 재시작·브라우저 초안 및 요청 키 복원을 검증했다. 합치기 UI는 제공하지 않는다.
- [x] 같은 브라우저 탭에서 채팅별 작성 중 입력·에이전트·모델·작업 경로·권한·자료·페이지/스크롤을 보존하고 프로젝트/채팅 전환·새로고침에서 복원한다. 같은 브라우저에서 탭 종료 후 복원과 빈 채팅 서버 저장도 구현했다. 여러 탭의 동시 편집·다른 기기 동기화는 후속 범위다. [복원 계약](client-runtime.md#채팅-작성-상태-복원--2026-09-17)
- [x] 한 채팅에서 Codex·Claude 전환 시 각 연결과 중간 결과를 보존한다. 모의 CLI로 재개·세션 ID 변경을 검증했다. 저장된 ID의 실제 원격 유효성 확인은 아래 실제 계정 검증에 남긴다.
- [x] 저장된 실행 상태와 종료 이벤트를 표시한다. 서버 재시작 후 소유하지 않은 실행은 SSE detached로 종료 미확인을 표시한다. 제어 가능한 실제 프로세스로 취소·강제 종료·재연결을 검증했다. 분석/검토 같은 내부 상태는 추정하지 않는다.
- [x] 신규·재개·새 네이티브 세션 시작·취소·실패 후 재시작을 자동 검사로 검증한다. 기존 프로젝트당 실행 제한을 유지하며 여러 세션 동시 실행은 별도 요구·격리 검토 후 결정한다.
- [x] 알림을 저장된 종료 이벤트와 연결했다. 짧은 실행·오프라인 완료·재접속·읽음 상태 복원을 검증했다. 최근 100개 표시, 브라우저별 읽음 상태이며 기기 간 동기화는 후속 범위다.
- [ ] 실제 전달 프롬프트·응답·세션 ID·작업 경로·적용 규칙·선택 자료·관련 파일 상태의 기록 부족분을 보완한다. 비밀정보를 불필요하게 복제하지 않는다.
- [ ] 하네스 재시작 복원, 원본 CLI 직접 재개, DB 백업·복원을 각각 검증한다. 데스크톱에 기록이 보이는지는 별도 확인한다.
- [x] 요청 ID 기반 중복 실행 방지를 구현하고 재전송·재시작·이름 변경 후 같은 요청 복원을 검증했다. 종료 이벤트도 중복 저장하지 않는다.

완료 기준: 새 채팅→에이전트 실행→다른 채팅 전환→복귀→재개 흐름에서 기록·입력·실행 대상이 뒤섞이지 않는다.

## 5. 대화 표시와 기존 제어 기능 연결

채팅 내용의 표현 방식은 수정 필요하다는 사용자 요청이 있다. 콘솔 크기가 정보 정리를 대신하지 않는다. 아래 표시 방식은 제안이며 실제 예시로 검토한다.

- [ ] 요청→진행→결과를 한 묶음으로 보여주고 명령·도구 로그는 접어서 볼 수 있게 한다. 변경·검증·미해결·사용자 판단 항목을 구분한다. 내부 추론을 노출하지 않는다.
- [ ] 메시지 길이·코드·로그에 맞는 읽기 폭, 콘솔 확장, 자동 스크롤 중지·새 출력 안내를 검증한다.
- [ ] 입력부 에이전트·모델·권한·참고 자료가 실제 요청과 일치하도록 연결한다. `/codex`, `/claude`의 명시적 선택 우선순위와 미지원 명령 거절을 유지한다.
- [ ] 기존 RuleLoader의 공통 가이드·프로젝트 규칙 자동 적용과 해시 기록을 유지한다. 메뉴에서 실제 적용 범위를 확인하도록 연결한다.
- [ ] 문서 열기와 참고 파일 첨부를 구분하고 기존 편집·저장·미저장 변경 확인·파일 경계를 유지한다.
- [ ] 질문·가설·방향 변경을 구분하는 지침의 실제 행동을 평가한다. `note/run` 구분 자체가 이 기능을 구현한 것으로 간주하지 않는다.
- [ ] 명시적으로 요청한 스킬·플러그인은 사용 가능/불가/확인 불가를 구분하고 실제 사용 근거만 표시한다.

완료 기준: 한 요청의 진행과 결과를 쉽게 구별하고, 메뉴 조작으로 작성 내용이나 실행 대상을 잃지 않는다.

- [ ] 파일 업로드 즉시 로컬 추출 → 프로젝트별 정제 규칙 적용 → 정제본 저장 → 색인/요약/AI 전달 순서를 적용한다. 원본이 정제보다 먼저 외부 모델·외부 OCR·임베딩 서비스로 전달되지 않게 한다.
- [ ] Excel·Word·CSV·TXT·MD를 대상으로 지원 확장자·크기·인코딩·실패 상태를 명시한다. PPT/PDF 화면설계서 분석과 연결하되 모든 형식을 처음부터 지원한다고 표시하지 않는다.
- [ ] 설정 UI에 파일 종류/이름, 엑셀 시트/열, 정확한 문자열/정규식/열 전체, 부분 마스킹/고정 치환/일관된 가상 값 치환/제외, 예외 범위와 규칙 적용 순서를 제공한다. 겹치는 규칙과 잘못된 정규식의 동작을 검증한다.
- [ ] 원본 파일을 무작정 문자열 치환하지 않고 형식별 셀·문단·표·열 구조를 읽어 처리한다. 초기 목표는 AI용 정제 텍스트·구조 데이터이며 서식 보존 사본 생성과 분리한다.
- [ ] 화면설계서·요구사항정의서는 대체로 마스킹 수요가 적다는 사용자 판단을 반영해 필요한 규칙만 적용한다. 우선 사용 사례는 엑셀 다운로드 테스트 데이터 정제다. 문서 종류만으로 민감정보가 없다고 단정하지 않는다.
- [ ] 대용량 엑셀은 선택한 시트/열만 순차 처리하고 메모리·진행률·취소를 관리한다. 고정 형식은 길이/접두어/문자열 연산, 필요한 패턴은 사전 컴파일 정규식을 사용한다. 압축 해제·파싱을 포함한 실제 병목과 처리량을 측정하고 정규식 과부하도 제한한다.
- [ ] 같은 원래 값은 시트·자료 사이에서도 일관된 가상 값으로 연결할 수 있게 한다. 복원 매핑이 필요한 경우 로컬 보호 저장하고 AI 입력·로그·공개 Git에 포함하지 않는다.
- [ ] 처리 결과에 유형별 정제 건수·제외·실패·미지원 내용을 표시하고 선택적으로 미리보기한다. 숨김 시트·주석·문서 메타데이터·내장 이미지/OCR·수식 등은 지원 여부를 명시한다. 실패/미지원 자료를 원본으로 대신 전송하지 않는다.
- [ ] 원본 보관 영역을 AI/CLI가 읽을 수 있는 작업 영역과 분리하고 실제 접근 경계를 검증한다. 폴더 분리만으로 접근 차단을 보장하지 않는다. 로그·오류·임시 파일·검색 결과에도 원문이 새지 않도록 한다.
- [ ] 규칙 변경 시 정제본·색인·파생 요약의 버전을 갱신하고 오래된 결과를 재사용하지 않는다. 이미 전달된 내용은 회수되지 않으므로 네이티브 세션 재사용 여부도 처리 정책에 포함한다.
- [ ] 엑셀 테스트용 마스킹 사본 생성은 동일 규칙 엔진을 공유하는 별도 후속 기능으로 둔다. 원본은 덮어쓰지 않는다.

완료 기준: 가짜 민감정보를 넣은 지원 형식에서 업로드부터 AI 전달까지 정제본만 사용함을 확인하고, 실패·규칙 변경·취소·재시작·대용량 처리에서 원본 유출과 오래된 정제본 재사용이 없음을 검증한다.

#### B. 필요한 자료 요청과 연결·증분 재사용

- [ ] 작업에 필요한 자료 목록을 저장된 자료와 대조하고 부족한 것만 사용자에게 요청한다. 예: DB 종류/버전과 DDL(PK/FK·인덱스·제약·주석), API 명세/권한/오류 정의, 요구사항 코드, 화면설계서 일부 페이지, 퍼블리싱 소스. 이미 등록된 자료를 다시 요구하지 않는다.
- [ ] 통 DDL을 등록하면 SQL 방언에 맞게 테이블·컬럼·키·관계를 분리해 저장한다. 실제 데이터 INSERT/덤프와 구분하고 프로젝트 자료는 기존 개인 데이터 공개 제외 규칙을 따른다.
- [ ] 요구사항 분류 코드 → 화면/동작 → 프론트 컴포넌트 → API/서비스 → 테이블/컬럼 → 테스트의 관계를 저장한다. 원문 파일·페이지/위치·버전·확정/추정/확인 필요 상태를 함께 연결한다. FK 없는 관계를 이름만 보고 확정하지 않는다.
- [ ] 원문/정제 규칙/파서 버전과 내용 해시로 재분석 필요 여부를 판단한다. 같은 자료는 분석 결과를 재사용하고, 변경된 객체와 영향받는 관계·요약만 갱신한다. 삭제·이름 변경·파싱 실패도 처리한다.
- [ ] 작업 코드·정확한 이름·텍스트 검색과 관계를 이용해 필요한 근거만 제한된 입력으로 구성한다. 전체 DDL/문서를 매 요청마다 넣지 않으며 요약에서 근거가 부족하면 원문의 관련 부분을 추가 조회한다.
- [ ] SQLite를 활용한 객체·관계·출처·색인 저장부터 검토한다. Redis·별도 그래프 DB·벡터 DB를 선행 조건으로 두지 않는다. Codex/Claude와 채팅 변경 후에도 공통 프로젝트 지식을 조회한다.
- [ ] 최초 추출/분석 비용까지 포함해 전달 토큰·재스캔량·재사용률·처리 시간·누락/오연결을 측정한다. 반복할수록 토큰이 항상 줄어든다고 보장하지 않고 동일 작업 조건에서 비교한다.

완료 기준: 전체 DDL과 요구사항/화면 샘플을 한 번 등록한 뒤 관련 부분만으로 후속 작업을 구성하고, 자료 변경 후 오래된 관계가 사용되지 않으며 다른 세션에서도 근거를 재사용한다.

#### C. 산출물 기반 설계와 채팅 도식

- [ ] PPT 일부 페이지·화면설계서·요구사항정의서를 받아 분류 코드별 작업 후보와 빠진 자료·충돌을 표시한다. 기존 스토리보드 백로그와 통합하며 중복 기능을 만들지 않는다.
- [ ] 퍼블리싱이 있는 경우 재사용할 화면과 연결 작업을, 없는 경우 화면 구현 범위와 제안 설계를 구분한다. 원문 근거와 AI 제안을 섞어 확정하지 않는다.
- [ ] 채팅에서 IA·화면 구조·프론트↔API↔DB 흐름·ERD·테스트 연결을 도식으로 제공한다. 도식의 항목에서 원문 페이지·코드·API·테스트 근거를 확인하도록 한다.
- [ ] AI가 만든 간결한 구조 데이터를 앱이 렌더링하는 방식을 우선 검토한다. 매번 이미지 생성 모델을 호출하지 않으며 시각화 자체가 토큰 절감을 보장한다고 설명하지 않는다.
- [ ] 한 화면으로 자료 등록 → 정제 → 관계 추출 → 사용자 검토 → 도식 → 작업 입력까지 검증한 뒤 확장한다.

#### 도구 후보와 비용 결정

사용자 결정: 단순 패턴·지정 시트/열 정제는 가벼운 자체 구현을 우선하고 복잡한 공문서·이미지 자동 탐지는 필요할 때 솔루션을 검토한다. Presidio 전체 기능을 재구현하는 것이 아니다. 첨부 가드 1차에는 detect-secrets와 openpyxl/python-docx/python-pptx를 설치·통합했다. Presidio·Docling은 도입하지 않았다.

- [ ] 문서 추출 후보 [Docling 지원 형식](https://docling-project.github.io/docling/usage/supported_formats/), 도식 후보 [Mermaid ERD](https://mermaid.js.org/syntax/entityRelationshipDiagram)를 실제 샘플·성능·의존성으로 평가한다.
- [ ] 복잡한 민감정보 자동 탐지 후보 [Presidio](https://microsoft.github.io/presidio/)는 후순위로 둔다. 탐지 누락 가능성, 한국어·사내 패턴과 이미지 처리 범위를 확인한다.
- [ ] 세 도구 본체는 MIT 오픈소스지만 추가 모델/의존성 라이선스는 별도 확인한다. 로컬 자원과 AI 설계/코딩 사용량은 별도 비용이며 유료 외부 서비스 도입을 전제하지 않는다. 플러그인 하나로 전체 흐름이 해결된다고 간주하지 않는다.

- [ ] Markdown/텍스트부터 자료 등록·파싱 범위·크기·실패 상태를 정하고 PPT·Excel·HTML 등으로 확장한다.
- [ ] 요구사항→설계→검토→구현의 산출물 파일·버전·생성 에이전트·입력 자료·결정을 연결한다. 모든 작업에 고정 단계를 강제하지 않는다.
- [ ] 초안과 확정본을 구분하고 다음 에이전트에 지정 버전을 전달한다. “방금 나온 설계”의 대상이 여러 개면 확인한다.
- [ ] 기록·산출물 보관/삭제 정책을 정한다.

## 향후: 스토리보드 분석과 화면별 요구사항·테스트 조회

2026-09-16 사용자 요청으로 추가한 백로그다. 오늘의 기본 UI·코어 기능 구현 이후에 진행하며, DB 스키마나 분석 도구 선택은 아직 확정하지 않았다. 아래 단계별 산출물 흐름과 연결할 후속 기능이다.

- [ ] 스토리보드 한 페이지를 입력받아 화면 요소, 사용자 행동, 입력·검증 조건, 로딩·빈 결과·성공·실패 상태를 분석한다. 이미지·PDF·PPT의 실제 지원 범위는 구현 시 정한다.
- [ ] 동작의 표시 방식(모달·화면 이동·새 창)과 갱신 방식(전체 새로고침·부분 데이터 재조회·상태 초기화)을 구분한다. 전달값, 저장·취소·닫기 동작, 검색 조건·페이지·스크롤·입력값 유지 여부도 정리한다.
- [ ] 분석 결과를 명시된 사실·추정·확인 필요로 구분하여 사용자가 검토할 수 있게 한다. 원문에 없는 동작을 확정 요구사항으로 저장하지 않는다.
- [ ] 화면 ID → 동작 → 요구사항 ID → 테스트케이스 ID의 관계를 DB에 저장하고 화면번호로 관련 내용을 조회한다. 여러 화면에서 공유하는 요구사항과 여러 요구사항을 검증하는 테스트의 연결도 고려한다. 관계 조회를 위해 별도 그래프 DB 도입을 전제하지 않는다.
- [ ] 원문 파일·페이지/위치, 버전, 초안·확정·폐기 상태를 연결한다. 원문과 DB 중 수정 기준을 정하고, 변경·삭제 시 연결을 갱신하며 영향받은 테스트를 재검토 대상으로 표시한다.
- [ ] 화면별 관련 요구사항 본문·완료 조건·테스트 정의와 필요한 화면 자료를 작업 입력으로 구성한다. ID만 전달하거나 전체 문서를 매번 일괄 주입하지 않는다. 테스트 정의와 실제 테스트 코드·실행 결과를 구분한다.
- [ ] 화면 한 페이지로 추출→사용자 검토→저장→조회→작업 전달을 검증한다. 변경 후 오래된 정의가 사용되지 않는지 확인하고, 초기 추출·갱신 비용까지 포함해 반복 문서 읽기 대비 토큰·시간·누락률을 비교한다.

완료 기준: 화면번호로 해당 버전의 요구사항과 테스트 정의를 원문 근거와 함께 조회하여 작업에 전달할 수 있고, 미확정 항목 및 변경으로 재검토가 필요한 항목을 식별할 수 있다. 실제 구현·테스트 성공은 별도 검증 결과로 판단한다.
