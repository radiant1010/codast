## 목표와 우선순위 변경

사용자는 하나의 CLI 대화에서 `/codex`, `/claude`로 에이전트를 직접 선택한다. 첨부 자료에서 요구사항을 도출하고, 설계·검증 산출물을 이어받아 구현한다. 오른쪽은 실행 과정이 실시간으로 올라오는 CLI이며 왼쪽은 접을 수 있는 문서·설정 제어판이다. 기존 탭·결과 카드 중심 화면은 최종 UI가 아니다.

기존의 ‘Claude 실환경 검증부터’ 또는 ‘실행 기록 검색 기능부터’ 순서를 대체한다. 다음 작업은 공통 실행·산출물·사용자 승인 계약을 정의하고 예약 명령어와 실시간 실행 이벤트를 연결하는 것이다. UI는 합의한 좌우 구조로 함께 개편한다. Claude는 회사 계정 연결 시 실검증하며 개인 결제를 선행 조건으로 두지 않는다.

## 1. 개발 가이드와 기존 아키텍처 기준 정의

[공통 개발 가이드](development-guide.md)를 RuleLoader에 연결했다. 기존·신규 프로젝트의 매 실행과 규칙 조회 화면에 포함하며 실행 메타데이터에 규칙별 SHA-256을 기록한다. 기존 프로젝트 RULES.md는 덮어쓰지 않는다. 34 passed / 1 skipped. 지침 전달은 완료했지만 프로젝트별 영향 분석과 승인 전 적용 차단은 아래 후속 작업으로 남아 있다.

- [ ] 프로젝트의 기존 룰북·설계 문서·아키텍처 결정 기록과 실제 코드를 확인하여 현재 구조·의존 관계·변경 영향 범위를 정리한다. 자료가 없거나 충돌하여 중요한 변경 영향을 판단하기 어려우면 사용자에게 확인한다.
- [x] 공통 개발 가이드 초안 작성: 테스트 FIRST, OOP·SOLID, 클린 코드, 낮은 결합도와 필요한 확장성.
- [ ] FIRST의 빠름·독립성·반복 가능성·자체 판정·적시성을 테스트 판단 기준으로 명시한다. FIRST를 일괄 TDD 강제로 해석하지 않는다. TDD는 사용자가 요청한 작업 방식에 따라 적용한다.
- [ ] 기존 설계·아키텍처 구조 변경은 보수적으로 처리한다. 사이드 이펙트, 호출부·의존 코드의 동작 불능, 호환성 저하 가능성을 먼저 검토한다. 기존 구조를 무조건 유지하거나 클린 코드·SOLID를 이유로 재편하지 않고, 변경 필요성과 영향에 근거해 판단한다.
- [ ] 과도한 추상화·불필요한 인터페이스·상속 계층·패턴 적용을 피하고 작업 규모에 맞는 설계를 사용한다.
- [ ] 중복 제거·상속은 예시임을 명시한다. 재사용·조합·추출·상속·신규 구현은 실제 맥락에 따라 판단하며 특정 기법을 기본 해법으로 강제하지 않는다.
- [ ] 공통 가이드·프로젝트 규칙·사용자 요청의 적용 범위와 충돌 확인 절차를 정의한다. 실행에 사용한 규칙 버전을 기록한다.

완료 기준: 가이드와 아키텍처 경계를 사용자가 검토할 수 있는 문서로 만들고, 아래 승인 흐름과 연결할 항목을 명확히 한다.

## 2. 예약 명령어와 실행 계약

- [ ] `/codex 요청`, `/claude 요청`을 파싱하여 지정한 에이전트로 실행한다. 지원하지 않는 명령은 설명하고 임의의 에이전트로 대체하지 않는다.
- [ ] 명령, 선택 자료, 작업·세션, 입력 산출물 버전, 적용 규칙, 권한, 결과를 하나의 실행 기록으로 연결한다.
- [ ] 앞 단계의 분석·설계·검토 결과를 다음 에이전트가 참조하도록 한다. ‘지금 분석된 내용’, ‘방금 나온 설계’의 대상이 여러 개면 확인한다.
- [ ] 일반 후속 메시지의 대상 에이전트와 대상을 화면에 표시한다. 새 명시적 명령과 충돌하거나 대상이 불명확하면 확인한다.
- [ ] 사용자가 특정 스킬·플러그인 사용을 요청하면 네이티브 지원 방식으로 연결하고 사용 가능/확인 불가/사용 불가를 구분한다. 실제 사용 근거 없이 사용했다고 표시하지 않는다.

완료 기준: 같은 작업에서 Codex → Claude → Codex로 요청과 지정한 산출물을 이어갈 수 있다. Claude 미설치 상태에서도 명령 파싱·전달 계약은 테스트할 수 있다.

## 3. 실시간 CLI와 접이식 제어판

- [ ] 상단 탭 중심 화면을 왼쪽 접이식 제어판 + 오른쪽 CLI로 개편한다. 사이드바 전체와 내부 섹션을 접고 펼칠 수 있게 한다.
- [ ] 왼쪽에 프로젝트·작업/세션·문서 목록·MD 미리보기·Context 선택 체크·실행 설정을 배치한다.
- [ ] 오른쪽에 사용자 명령·에이전트 응답·파일 작업·도구 실행·완료·오류를 시간순으로 표시한다. 지원되는 실제 이벤트만 출력한다.
- [ ] 입력창을 오른쪽 하단에 고정하고 실행 중 상태·중지·사용자 응답 대기를 표시한다.
- [ ] CLI 어댑터의 이벤트 수집 및 브라우저 전송을 구현한다. 재접속 시 이벤트 순서·중복·누락과 최종 기록 복원을 검증한다.
- [ ] 왼쪽에서 문서를 읽는 것과 에이전트에게 전달하는 선택을 구분한다. 긴 출력 탐색 중 자동 스크롤로 읽던 위치를 빼앗지 않는다.

완료 기준: 실행이 끝나기 전 진행 이벤트를 볼 수 있고, 왼쪽 설정을 조작해도 오른쪽 대화와 입력을 유지한다.

## 4. 첨부 자료와 단계별 산출물

- [ ] 첨부·선택한 자료를 입력으로 등록하고 파싱 지원 범위·크기 제한·실패 상태를 표시한다. 우선 Markdown/텍스트부터 완결하고 PPT·Excel·HTML 등으로 확장한다.
- [ ] 요구사항 정의서 → 기능 설계 → 설계 검토/수정 → 구현의 기본 흐름을 제공한다. 모든 작업에 고정된 단계 통과를 강요하지 않는다.
- [ ] 산출물을 실제 파일로 저장하고 작업·생성 에이전트·입력 자료·버전·검토 상태·관련 결정을 연결한다.
- [ ] 다음 단계에서 사용할 산출물을 명확히 지정하고 최신 초안과 사용자가 확정한 버전을 구분한다.
- [ ] 왼쪽에서 산출물을 열고 다음 요청의 참고 자료로 선택할 수 있도록 한다.

완료 기준: 첨부 문서에서 만든 요구사항을 다른 에이전트가 설계로 발전시키고, 검토한 설계 버전을 명시하여 구현에 전달한다.

## 5. 아키텍처 변경 알림·사용자 판단·재개

- [ ] 기존 구조 안의 내부 개선과 사용자 판단이 필요한 구조 변경을 구분한다. 주요 대상은 계층 간 의존성, 모듈 책임, 공개 인터페이스, 공통 기반 구조 변경이다.
- [ ] 판단 필요 시 변경 이유·영향받는 코드·예상 사이드 이펙트·호환성 위험·검증 계획·대안·추천안을 표시하고 해당 변경을 대기시킨다. 영향이 크거나 불확실한 구조 변경은 사용자 판단 후 진행하며, 작고 일상적인 변경에 일괄 승인을 요구하지 않는다.
- [ ] 사용자에게 승인·유지·대안 선택을 받아 작업을 재개하고 결정 근거를 저장한다.
- [ ] 승인 범위를 제안한 변경과 기준 코드/설계 버전에 묶는다. 중요한 내용이 바뀌면 이전 승인을 자동 재사용하지 않는다.
- [ ] 룰북 안내만으로 변경 차단을 보장하지 않는다. 실제 CLI별 도구/승인 인터페이스를 조사하고 읽기 전용 사전 검토 또는 변경안 분리 등으로 승인 전 적용을 막는 방식을 설계·검증한다.
- [ ] 대기 상태를 DB에 저장하여 재시작 후 질문과 결정을 복원하고, 재개 과정의 중복 실행을 방지한다.

완료 기준: 아키텍처 변경 시나리오에서 사용자 판단 전 대상 변경이 적용되지 않으며, 승인·거절·서버 재시작 후에도 올바르게 이어간다. 이 경로를 검증하기 전에는 구조 변경 통제가 완성됐다고 표시하지 않는다.
