# 공통 개발 가이드

이 가이드는 설계·구현·검토의 판단 기준이다. 특정 패턴이나 절차를 모든 작업에 일괄 적용하지 않는다. 프로젝트의 기존 규칙과 실제 코드를 함께 확인하고 작업 규모에 맞게 적용한다.

## 적용 범위와 판단 순서

- 사용자 요청과 승인된 작업 범위를 먼저 확인하고, 관련 프로젝트 규칙·설계 문서·실제 구현을 읽는다. 현재 필요한 동작과 유지해야 하는 기존 동작을 구분한다.
- 이 가이드는 공통 기본값이다. 상위 지침과 사용자의 명시적 요구를 우선하며, 프로젝트별 규칙은 해당 범위에서 함께 적용한다. 파일을 읽은 순서가 규칙의 우선순위를 뜻하지 않는다.
- 규칙 사이에 충돌이 있으면 적용 범위와 근거를 확인한다. 중요한 동작이나 구조에 영향을 주는 충돌만 사용자에게 확인하며, 명확히 허용된 일상적 작업까지 매번 승인을 요구하지 않는다.
- 구현 전에 기존 기능·공통 코드·의존성을 확인한다. 이미 해결된 문제를 다시 만들지 않되, 단지 비슷해 보인다는 이유로 서로 다른 책임을 무리하게 통합하지 않는다.
- 요구사항을 충족하는 가장 단순한 설계를 우선한다. 미래에 필요할지도 모른다는 이유로 기능, 설정 항목, 확장 지점, 플러그인 체계나 범용 프레임워크를 추가하지 않는다.

## 설계와 구현

- OOP·SOLID·클린 코드 원칙을 참고하여 책임을 명확히 하고 결합도를 낮추며 필요한 변경과 확장이 쉬운 코드를 작성한다.
- 원칙 준수 자체를 목표로 불필요한 인터페이스, 추상 계층, 상속 구조, 디자인 패턴을 추가하지 않는다. 예상만으로 범용 프레임워크를 만들지 않는다.
- 기존 코드와 관례를 먼저 조사한다. 중복 제거·상속은 가능한 선택지일 뿐 의무가 아니다. 재사용·조합·공통 기능 추출·상속·신규 구현 중 실제 요구와 영향에 적합한 방법을 선택한다.

## 기능과 책임의 분리

- 변경 이유가 다른 책임을 분리한다. 하나의 관리자 객체에 프로젝트 관리·자료 구성·실행·저장·승인 처리를 계속 누적하지 않는다. 규모가 작고 함께 변경되는 기능은 한 모듈에 유지할 수 있다.
- HTTP API가 있는 프로젝트에서는 API가 입력 검증·서비스 호출·응답 변환을 담당하고, 업무 판단은 서비스에 둔다. API에서 SQL이나 실행 가능 여부 등의 업무 규칙을 직접 처리하지 않는다.
- 데이터 접근과 SQL은 저장소에 모으고, 파일·외부 CLI 같은 시스템 접근은 해당 기능의 담당 모듈에 둔다. 특정 프레임워크나 저장 방식이 바뀌어도 관련 없는 업무 코드까지 수정하지 않도록 경계를 정한다.
- 이 역할 구분은 모든 기능에 API → 서비스 → 저장소 클래스를 기계적으로 만들라는 뜻이 아니다. 의미 없는 전달 메서드나 계층은 추가하지 않는다.
- 동기 파일·DB 작업과 외부 프로세스 처리가 다른 요청을 불필요하게 막지 않도록 실행 방식을 검토한다. 비동기 선언만으로 병렬 처리나 안전한 취소가 보장된다고 가정하지 않는다.

## SOLID·OOP의 실용적 적용

- 단일 책임(S): 클래스·모듈은 일관된 책임을 갖는다. 단순히 파일이 길다는 이유보다 서로 다른 이유로 변경되는지를 기준으로 나눈다.
- 개방·폐쇄(O): 실제로 변형이 존재하는 지점은 구현을 추가하기 쉽게 만든다. 모든 변경을 대비하는 추상화를 미리 만들지 않는다.
- 리스코프 치환(L): 공통 계약의 구현들은 호출자가 기대하는 입력·결과·실패·취소 동작을 지킨다. 구현을 바꿀 때 호출자가 예외적인 분기를 알아야 한다면 계약을 재검토한다.
- 인터페이스 분리(I): 호출자가 사용하는 작은 계약만 제공한다. 일부 구현에서 의미 없는 메서드를 강제로 구현하게 하지 않는다.
- 의존성 역전(D): 실행·업무 판단이 구체적인 CLI나 저장 구현을 직접 선택하는 조건문에 과도하게 의존하지 않게 한다. 구현 선택과 조립은 진입점에 모으고, 교체·테스트에 필요한 경계부터 계약을 둔다. 모든 클래스에 인터페이스를 만들 필요는 없다.
- OOP는 관련 상태와 동작을 묶고 내부 규칙을 보호하는 데 사용한다. 상태가 없는 단순 변환은 함수로 표현해도 된다. 상속보다 객체 조합을 우선 검토하며, 실제로 같은 계약을 대체할 때만 상속을 사용한다.
- 원칙의 예외나 절충이 필요하면 현재 요구, 더 단순한 대안, 영향과 이유를 설명한다. 사소한 구현 선택마다 별도 설계 문서를 작성하지 않는다.

## 부하·신뢰성에 대한 설계 판단

- 변경과 관련 있는 성능·부하, 멱등성, 동시성, 데이터 일관성, 실패·재시도, 상태 복구, 원인 추적 가능성을 검토한다. 모든 작업에 같은 대책을 강제로 적용하지 않는다.
- 예상 사용자 수·동시 실행 수·파일 및 로그 크기·허용 지연을 가정으로 명시한다. 처리 용량과 병목은 관련 환경에서 측정하며 추정치와 실측치를 구분한다. 검증하지 않은 성능을 보장하지 않는다.
- 중복 요청이나 재시도가 부작용을 반복할 수 있는지 확인한다. 멱등성 보장 범위, 요청 식별, 동시 요청 처리, 보관 기간과 실패 후 동작은 필요할 때 구체화한다. 단순 실행 제한을 중복 실행 방지 보장으로 간주하지 않는다.
- 파일·DB·외부 프로세스가 함께 변경되는 경우 일부만 성공하거나 서버가 재시작되는 상황을 검토한다. 실패를 안전하게 확인·복구하는 데 필요한 범위만 구현한다.
- AI는 요구와 근거를 바탕으로 대안을 제안·검증한다. 중요한 비용·호환성·복구 수준·구조 변경의 절충은 사용자에게 설명하며, 이미 승인된 범위를 넘어 임의로 결정하지 않는다. 큐·캐시·분산 처리 같은 수단을 검토 항목이 있다는 이유만으로 도입하지 않는다.

## 판단 근거와 레퍼런스

- 설계·아키텍처·기술 선택을 제안하거나 결정할 때 해당 판단을 뒷받침하는 레퍼런스 링크를 반드시 첨부한다. 링크는 관련 주장 가까이에 두고, 무엇을 뒷받침하는지 설명한다.
- 외부 기술 사실은 공식 문서·표준·원 논문 등 1차 자료를 우선한다. 검색 결과나 홈페이지 대신 실제 근거가 있는 페이지·절에 직접 연결한다. 적용 중인 버전과 실행 환경에 맞는 내용인지 확인한다.
- 기존 코드·프로젝트 규칙에 근거한 판단은 해당 파일과 필요한 위치로 연결한다. 측정·테스트에 근거한 판단은 검증 기록 링크와 조건·방법·결과를 함께 남긴다. 외부 문서로 로컬 구현의 정확성이나 처리 용량을 입증한 것처럼 설명하지 않는다.
- 확인한 사실, 가정, 측정 결과, AI의 해석·추천을 구분한다. 출처가 설명하는 일반 원칙이 이 프로젝트의 특정 설계를 반드시 요구한다고 확대 해석하지 않는다.
- 실제 확인하지 않은 자료나 존재하지 않는 링크를 인용하지 않는다. 근거를 확인할 수 없으면 확인 불가·미검증임을 명시하고 결론의 한계와 필요한 확인을 설명한다. 중대한 판단에 필요한 근거가 부족하면 확정하지 않는다.
- 기록의 기본 형태는 ‘판단 → 이유·대안 → 근거 링크 → 적용 조건·검증’으로 한다. 중요한 결정은 관련 설계 문서나 결정 기록에 남기되, 사소한 변경마다 별도 문서나 반복적인 외부 검색을 강제하지 않는다. 동일한 범위와 버전에 대해 이미 확인한 근거는 재사용할 수 있다.

## 테스트

- FIRST를 판단 기준으로 삼는다: 빠름(Fast), 독립성(Independent), 반복 가능성(Repeatable), 자체 판정(Self-validating), 적시성(Timely).
- 변경된 동작과 주요 실패 경로를 검증하는 의미 있는 테스트를 작성한다. 구현을 그대로 복제하는 테스트나 불필요한 검증 절차를 늘리지 않는다.
- FIRST를 모든 작업에 TDD를 강제하는 규칙으로 해석하지 않는다. 사용자가 TDD를 요청하면 실패하는 테스트 → 필요한 구현 → 테스트 통과 → 리팩터링 순서로 진행한다.

## 기존 설계·아키텍처 구조 변경

- 기존 설계·아키텍처 구조 변경은 보수적으로 처리한다. 기존 구조를 무조건 유지한다는 뜻도, 클린 코드·SOLID를 이유로 재편해도 된다는 뜻도 아니다.
- 변경 전에 설계 문서·프로젝트 규칙·실제 코드의 의존 관계와 호출부를 확인한다. 사이드 이펙트, 다른 코드의 동작 불능, 공개 인터페이스·데이터·설정의 호환성 저하 가능성을 검토한다.
- 영향이 크거나 불확실한 구조 변경은 바로 적용하지 않는다. 특히 계층 간 의존성, 모듈 책임, 공개 인터페이스, 공통 기반 구조를 바꿀 때 영향 범위를 확인한다.
- 사용자 판단이 필요하면 변경 이유, 영향받는 코드, 예상 사이드 이펙트·호환성 위험, 기존 구조를 유지하거나 변경을 줄이는 대안, 추천안과 근거, 검증 계획을 설명한다. 해당 변경은 사용자 판단 전까지 보류한다.
- 질문을 띄울 수 없는 실행 환경에서도 임의로 승인된 것으로 간주하지 않는다. 응답에 ‘사용자 판단 필요’와 구체적인 질문을 남기고 해당 변경을 적용하지 않은 상태로 마친다.
- 작고 일상적이며 영향이 확인된 내부 개선에는 일괄 승인을 요구하지 않는다. 승인된 변경의 범위나 중요한 전제가 달라지면 다시 확인한다.
- 프로젝트 규칙·설계 문서가 없거나 충돌하여 중요한 영향을 판단할 수 없으면, 추측으로 새 구조를 확정하지 말고 불확실한 부분을 설명한다.

## 결과 보고

- 변경 내용, 이유, 검증 결과, 남은 문제와 설계에서 달라진 점을 구분하여 보고한다. 수행하지 않은 검사나 사용하지 않은 도구를 사용했다고 표시하지 않는다.
- 사용자 판단을 받은 경우 결정과 적용 범위를 결과에 남긴다. 관련 없는 변경에 그 승인을 확대 적용하지 않는다.

## 변경과 검증의 크기

- 기존 API·기록·세션·파일 동작을 보존하면서 작은 단위로 책임을 옮긴다. 리팩터링에 관계없는 기능 추가나 UI 변경을 섞지 않는다.
- 변경 범위에 맞는 동작·실패 경로·호환성 검증을 수행한다. 문서·간격 같은 저위험 변경에 불필요한 테스트를 추가하지 않는다. 기존 검증이 충분하면 같은 내용을 중복 검증하지 않는다.
- 가이드 작성, 코드에서의 준수, 시스템 차원의 승인·변경 차단은 별개다. 문서에 원칙을 적었다는 이유로 리팩터링이나 승인 기능이 완료됐다고 보고하지 않는다.
