# 공통 개발 가이드

이 가이드는 설계·구현·검토의 판단 기준이다. 특정 패턴이나 절차를 모든 작업에 일괄 적용하지 않는다. 프로젝트의 기존 규칙과 실제 코드를 함께 확인하고 작업 규모에 맞게 적용한다.

## 적용 범위와 판단 순서

- 사용자 요청과 승인된 작업 범위를 먼저 확인하고, 관련 프로젝트 규칙·설계 문서·실제 구현을 읽는다. 현재 필요한 동작과 유지해야 하는 기존 동작을 구분한다.
- 이 가이드는 공통 기본값이다. 상위 지침과 사용자의 명시적 요구를 우선하며, 프로젝트별 규칙은 해당 범위에서 함께 적용한다. 파일을 읽은 순서가 규칙의 우선순위를 뜻하지 않는다.
- 규칙 사이에 충돌이 있으면 적용 범위와 근거를 확인한다. 중요한 동작이나 구조에 영향을 주는 충돌만 사용자에게 확인하며, 명확히 허용된 일상적 작업까지 매번 승인을 요구하지 않는다.
- 구현 전에 기존 기능·공통 코드·의존성을 확인한다. 이미 해결된 문제를 다시 만들지 않되, 단지 비슷해 보인다는 이유로 서로 다른 책임을 무리하게 통합하지 않는다.
- 요구사항을 충족하는 가장 단순한 설계를 우선한다. 미래에 필요할지도 모른다는 이유로 기능, 설정 항목, 확장 지점, 플러그인 체계나 범용 프레임워크를 추가하지 않는다.

## 대화 해석과 목표 유지

- 실행 요청을 받으면 현재 목표·완료 조건·제약·승인 범위를 확인하고 필요한 작업을 완료할 때까지 진행한다. 실행을 요청한 사용자에게 가능 여부나 계획만 답하고 끝내지 않는다. 의견·설명 요청 자체를 구현 승인으로 확대하지 않는다.
- 후속 메시지는 기존 작업 맥락과 함께 해석한다. 사용자가 취소·교체하지 않은 목표와 유효한 결정은 유지한다. 명시적인 변경·중단 지시는 반영하고, 바뀐 범위와 영향을 짧게 알린다.
- 질문, 가설, 변경 지시를 구분한다. “왜 A로 했어?”에는 근거를 설명하고 기존 작업을 이어간다. “C도 가능해?”에는 대안을 검토하되 적용을 승인받았다고 간주하지 않는다. “C로 바꿔”에는 변경 범위를 반영한다. 문장 형식만으로 분류하지 않고 앞선 맥락과 의도를 함께 본다.
- 질문에 새로운 사실이나 오류 근거가 포함되면 검증하고 필요한 판단을 수정한다. 목표 유지가 잘못된 결론을 고수하는 이유가 되어서는 안 된다. 의도가 모호하고 해석 차이가 중요한 변경을 유발할 때만 해당 부분을 확인한다.
- 사용자와 AI의 가설은 검증된 사실과 구분한다. 결론에 중요한 가설은 실제 코드·로그·문서와 반례로 확인한다. 동의나 반대 자체를 목표로 삼지 않으며, 모든 작업에 복수 에이전트나 정해진 수의 대안을 강제하지 않는다.

## 자율 진행과 사용자 판단

- 이미 허용된 조사·구현·검증과 일상적인 내부 선택은 스스로 진행한다. 기존 승인의 범위와 중요한 전제가 유지되면 다시 승인받지 않는다. 진행 상황 공유는 응답 대기 요청과 구분한다.
- 사용자 판단이 필요한 경우는 필수 정보가 없거나, 사용자 의도·제품 정책으로 결정해야 하거나, 승인 범위를 벗어나거나, 아래 구조 변경 기준에 해당하는 경우다. 단지 선택지가 여러 개이거나 도구를 실행한다는 이유만으로 멈추지 않는다.
- 판단 요청 전에 승인 범위 안에서 가능한 조사·대안 비교·검증을 마친다. 무엇을 확인했고 무엇이 미확정인지, 선택지와 영향, 추천과 근거, 필요한 결정 및 대기 중인 작업을 제시한다. 승인 대상 변경 자체를 미리 적용하지 않는다.
- 정보 부족과 승인 대기를 구분한다. 전자는 필요한 사실을, 후자는 준비된 변경에 대한 결정을 요청한다. 답변이 없어도 진행 가능한 독립 작업은 계속하되 침묵·시간 경과를 승인으로 취급하지 않는다.
- 규칙·스킬 때문에 중단해야 한다면 정확한 파일·조항과 적용 이유를 알린다. 명시적 금지와 AI의 보수적 해석을 구분하고, 기존 승인과 해당 규칙의 적용 범위를 먼저 확인한다. 가상의 위험만으로 승인 절차를 추가하지 않는다.

## 맥락 보존과 재개

- 장기 작업의 인수인계에는 목표·완료 조건·제약, 확정 결정과 적용 범위, 기각한 대안과 이유, 미해결 질문, 완료·남은 작업, 검증 결과를 필요한 만큼 남긴다. 중요한 판단은 원문·파일·실행 기록으로 추적할 수 있게 한다. AI의 제안을 사용자 확정 결정으로 기록하지 않는다.
- 요약이나 이전 세션의 기억을 현재 파일 상태보다 우선하지 않는다. 재개 시 관련 파일·작업 경로·Git 상태와 입력 버전을 확인하고, 달라진 전제의 영향을 검토한다. 이미 완료한 작업은 근거 없이 반복하지 않는다.
- 현재 작업에 필요한 규칙·자료·결정만 전달하되 핵심 제약을 임의로 생략하지 않는다. 컨텍스트가 부족하면 관련 원문을 추가 확인하고 누락 사실을 숨기지 않는다. 오래된 색인·요약은 갱신하거나 미확인 상태로 표시한다.

위 실행 기준은 [OpenAI 모델 가이드의 자율 진행·승인 시점](https://developers.openai.com/api/docs/guides/latest-model#initiative-and-follow-through)과 [지침 충돌 처리](https://developers.openai.com/api/docs/guides/latest-model#instruction-following)를 참고하여 이 프로젝트에 적용한 규칙이다(2026-09-16 확인). 모델별 권고를 모든 클라이언트의 동작 보장으로 해석하지 않는다. 질문·지시 구분과 맥락 보존은 사용자가 합의한 하네스 요구이며 실제 준수 여부는 별도로 검증한다.

## 설계와 구현

- OOP·SOLID·클린 코드 원칙을 참고하여 책임을 명확히 하고 결합도를 낮추며 필요한 변경과 확장이 쉬운 코드를 작성한다.
- 원칙 준수 자체를 목표로 불필요한 인터페이스, 추상 계층, 상속 구조, 디자인 패턴을 추가하지 않는다. 예상만으로 범용 프레임워크를 만들지 않는다.
- 기존 코드와 관례를 먼저 조사한다. 중복 제거·상속은 가능한 선택지일 뿐 의무가 아니다. 재사용·조합·공통 기능 추출·상속·신규 구현 중 실제 요구와 영향에 적합한 방법을 선택한다.

## 기능과 책임의 분리

- 변경 이유가 다른 책임을 분리한다. 하나의 관리자 객체에 프로젝트 관리·자료 구성·실행·저장·승인 처리를 계속 누적하지 않는다. 규모가 작고 함께 변경되는 기능은 한 모듈에 유지할 수 있다.
- HTTP API가 있는 프로젝트에서는 API가 입력 검증·서비스 호출·응답 변환을 담당하고, 업무 판단은 서비스에 둔다. API에서 SQL이나 실행 가능 여부 등의 업무 규칙을 직접 처리하지 않는다.
- 데이터 접근과 SQL은 저장소에 모으고, 파일·외부 CLI 같은 시스템 접근은 해당 기능의 담당 모듈에 둔다. 특정 프레임워크나 저장 방식이 바뀌어도 관련 없는 업무 코드까지 수정하지 않도록 경계를 정한다.
- 이 역할 구분은 모든 기능에 API → 서비스 → 저장소 클래스를 기계적으로 만들라는 뜻이 아니다. 의미 없는 전달 메서드나 계층은 추가하지 않는다.
- 동기 파일·DB 작업과 외부 프로세스 처리가 다른 요청을 불필요하게 막지 않도록 실행 방식을 검토한다. 비동기 선언만으로 병렬 처리나 안전한 취소가 보장된다고 가정하지 않는다.

## SOLID·OOP의 실용적 적용

- 단일 책임(S): 클래스·모듈은 일관된 책임을 갖는다. 단순히 파일이 길다는 이유보다 서로 다른 이유로 변경되는지를 기준으로 나눈다.
- 개방·폐쇄(O): 실제로 변형이 존재하는 지점은 구현을 추가하기 쉽게 만든다. 모든 변경을 대비하는 추상화를 미리 만들지 않는다.
- 리스코프 치환(L): 공통 계약의 구현들은 호출자가 기대하는 입력·결과·실패·취소 동작을 지킨다. 구현을 바꿀 때 호출자가 예외적인 분기를 알아야 한다면 계약을 재검토한다.
- 인터페이스 분리(I): 호출자가 사용하는 작은 계약만 제공한다. 일부 구현에서 의미 없는 메서드를 강제로 구현하게 하지 않는다.
- 의존성 역전(D): 실행·업무 판단이 구체적인 CLI나 저장 구현을 직접 선택하는 조건문에 과도하게 의존하지 않게 한다. 구현 선택과 조립은 진입점에 모으고, 교체·테스트에 필요한 경계부터 계약을 둔다. 모든 클래스에 인터페이스를 만들 필요는 없다.
- OOP는 관련 상태와 동작을 묶고 내부 규칙을 보호하는 데 사용한다. 상태가 없는 단순 변환은 함수로 표현해도 된다. 상속보다 객체 조합을 우선 검토하며, 실제로 같은 계약을 대체할 때만 상속을 사용한다.
- 원칙의 예외나 절충이 필요하면 현재 요구, 더 단순한 대안, 영향과 이유를 설명한다. 사소한 구현 선택마다 별도 설계 문서를 작성하지 않는다.

## 부하·신뢰성에 대한 설계 판단

- 변경과 관련 있는 성능·부하, 멱등성, 동시성, 데이터 일관성, 실패·재시도, 상태 복구, 원인 추적 가능성을 검토한다. 모든 작업에 같은 대책을 강제로 적용하지 않는다.
- 예상 사용자 수·동시 실행 수·파일 및 로그 크기·허용 지연을 가정으로 명시한다. 처리 용량과 병목은 관련 환경에서 측정하며 추정치와 실측치를 구분한다. 검증하지 않은 성능을 보장하지 않는다.
- 중복 요청이나 재시도가 부작용을 반복할 수 있는지 확인한다. 멱등성 보장 범위, 요청 식별, 동시 요청 처리, 보관 기간과 실패 후 동작은 필요할 때 구체화한다. 단순 실행 제한을 중복 실행 방지 보장으로 간주하지 않는다.
- 파일·DB·외부 프로세스가 함께 변경되는 경우 일부만 성공하거나 서버가 재시작되는 상황을 검토한다. 실패를 안전하게 확인·복구하는 데 필요한 범위만 구현한다.
- AI는 요구와 근거를 바탕으로 대안을 제안·검증한다. 중요한 비용·호환성·복구 수준·구조 변경의 절충은 사용자에게 설명하며, 이미 승인된 범위를 넘어 임의로 결정하지 않는다. 큐·캐시·분산 처리 같은 수단을 검토 항목이 있다는 이유만으로 도입하지 않는다.

## 판단 근거와 레퍼런스

- 설계·아키텍처·기술 선택을 제안하거나 결정할 때 해당 판단을 뒷받침하는 레퍼런스 링크를 반드시 첨부한다. 링크는 관련 주장 가까이에 두고, 무엇을 뒷받침하는지 설명한다.
- 외부 기술 사실은 공식 문서·표준·원 논문 등 1차 자료를 우선한다. 검색 결과나 홈페이지 대신 실제 근거가 있는 페이지·절에 직접 연결한다. 적용 중인 버전과 실행 환경에 맞는 내용인지 확인한다.
- 기존 코드·프로젝트 규칙에 근거한 판단은 해당 파일과 필요한 위치로 연결한다. 측정·테스트에 근거한 판단은 검증 기록 링크와 조건·방법·결과를 함께 남긴다. 외부 문서로 로컬 구현의 정확성이나 처리 용량을 입증한 것처럼 설명하지 않는다.
- 확인한 사실, 가정, 측정 결과, AI의 해석·추천을 구분한다. 출처가 설명하는 일반 원칙이 이 프로젝트의 특정 설계를 반드시 요구한다고 확대 해석하지 않는다.
- 실제 확인하지 않은 자료나 존재하지 않는 링크를 인용하지 않는다. 근거를 확인할 수 없으면 확인 불가·미검증임을 명시하고 결론의 한계와 필요한 확인을 설명한다. 중대한 판단에 필요한 근거가 부족하면 확정하지 않는다.
- 기록의 기본 형태는 ‘판단 → 이유·대안 → 근거 링크 → 적용 조건·검증’으로 한다. 중요한 결정은 관련 설계 문서나 결정 기록에 남기되, 사소한 변경마다 별도 문서나 반복적인 외부 검색을 강제하지 않는다. 동일한 범위와 버전에 대해 이미 확인한 근거는 재사용할 수 있다.

## 테스트

- FIRST를 판단 기준으로 삼는다: 빠름(Fast), 독립성(Independent), 반복 가능성(Repeatable), 자체 판정(Self-validating), 적시성(Timely).
- 변경된 동작과 주요 실패 경로를 검증하는 의미 있는 테스트를 작성한다. 구현을 그대로 복제하는 테스트나 불필요한 검증 절차를 늘리지 않는다.
- FIRST를 모든 작업에 TDD를 강제하는 규칙으로 해석하지 않는다. 사용자가 TDD를 요청하면 실패하는 테스트 → 필요한 구현 → 테스트 통과 → 리팩터링 순서로 진행한다.
- 필요한 검증이 통과하면 완료로 진행한다. 추가 변경·실패·미해결 우려가 있을 때만 검증을 확대하거나 반복한다. [OpenAI 검증 범위 가이드](https://developers.openai.com/api/docs/guides/latest-model#testing-and-verification)를 참고하되 프로젝트의 필수 검증을 생략하는 근거로 사용하지 않는다.

## 기존 설계·아키텍처 구조 변경

- 기존 설계·아키텍처 구조 변경은 보수적으로 처리한다. 기존 구조를 무조건 유지한다는 뜻도, 클린 코드·SOLID를 이유로 재편해도 된다는 뜻도 아니다.
- 변경 전에 설계 문서·프로젝트 규칙·실제 코드의 의존 관계와 호출부를 확인한다. 사이드 이펙트, 다른 코드의 동작 불능, 공개 인터페이스·데이터·설정의 호환성 저하 가능성을 검토한다.
- 영향이 크거나 불확실한 구조 변경은 바로 적용하지 않는다. 특히 계층 간 의존성, 모듈 책임, 공개 인터페이스, 공통 기반 구조를 바꿀 때 영향 범위를 확인한다.
- 사용자 판단이 필요하면 변경 이유, 영향받는 코드, 예상 사이드 이펙트·호환성 위험, 기존 구조를 유지하거나 변경을 줄이는 대안, 추천안과 근거, 검증 계획을 설명한다. 해당 변경은 사용자 판단 전까지 보류한다.
- 질문을 띄울 수 없는 실행 환경에서도 임의로 승인된 것으로 간주하지 않는다. 응답에 ‘사용자 판단 필요’와 구체적인 질문을 남기고 해당 변경을 적용하지 않은 상태로 마친다.
- 작고 일상적이며 영향이 확인된 내부 개선에는 일괄 승인을 요구하지 않는다. 승인된 변경의 범위나 중요한 전제가 달라지면 다시 확인한다.
- 프로젝트 규칙·설계 문서가 없거나 충돌하여 중요한 영향을 판단할 수 없으면, 추측으로 새 구조를 확정하지 말고 불확실한 부분을 설명한다.

## 개인 데이터와 공개 배포

2026-09-16 사용자 결정: 개인 설정, 실제 AI 연결·인증 정보, 채팅·실행 기록, SQLite 데이터와 SQL 데이터 덤프는 공개 저장소·Docker 이미지·배포 압축 파일에 포함하지 않는다. 이후 작업에도 적용하는 저장소의 지속 규칙이다.

- 공개 대상은 소스·스키마 DDL·마이그레이션·실제 값이 없는 설정 템플릿·가짜 테스트 데이터다. DDL과 개인 데이터 INSERT/덤프를 구분한다. 실제 계정 ID, 세션 ID, 토큰/키, 개인 연결 주소, 개인 설정값을 예제·테스트·SQL·스크린샷·문서에 복사하지 않는다.
- 로컬 파일을 새로 만들 때는 우선 제외된 `.local/`, `work/`, `outputs/` 등을 사용한다. 연결 설정은 `connections.local.json`, 개인 설정은 `settings.local.json` 등 제외 대상 이름을 사용한다. 기존 DB 경로를 이 규칙만으로 자동 이동하지 않는다.
- CLI 인증 저장소를 복제하지 않는다. 실행 로그·응답에도 비밀정보가 포함될 수 있으므로 공개 산출물에 원문을 무심코 옮기지 않는다. 점검 결과에는 값 대신 파일·위치·유형을 기록한다.
- Git 제외와 Docker 빌드 제외, git archive 제외는 별도로 유지한다. 임의 ZIP 생성은 이 규칙을 자동 적용하지 않으므로 공개 파일 목록을 명시해 패키징한다.
- 커밋·공개 전에 실제 staged 파일 및 diff를 확인한다. `.gitignore`는 이미 추적된 파일과 과거 이력을 제거하지 않으며, 파일명 규칙은 소스에 붙여 넣은 비밀값을 탐지하지 못한다. 제외 대상의 강제 추가(`git add -f`)를 하지 않는다.
- 이미 추적된 개인 데이터 발견 시 원본은 보존하고 공개 대상에서 제외한다. 과거 이력 재작성·원격 강제 푸시는 별도의 영향 확인과 사용자 승인 없이 하지 않는다. 노출된 인증 값이 확인되면 교체 필요성을 알린다.
- 개발 경로·localhost 예시만으로 인증정보 유출이라고 단정하지 않는다. 실제 개인 데이터와 일반 개발 설명을 구분한다. 이 룰북은 행동 기준이며 자동 비밀정보 차단 기능의 구현 완료를 의미하지 않는다.

## 결과 보고 기준

- 변경 내용, 이유, 검증 결과, 남은 문제와 설계에서 달라진 점을 구분하여 보고한다. 수행하지 않은 검사나 사용하지 않은 도구를 사용했다고 표시하지 않는다.
- 사용자 판단을 받은 경우 결정과 적용 범위를 결과에 남긴다. 관련 없는 변경에 그 승인을 확대 적용하지 않는다.

## 변경과 검증의 크기

- 기존 API·기록·세션·파일 동작을 보존하면서 작은 단위로 책임을 옮긴다. 리팩터링에 관계없는 기능 추가나 UI 변경을 섞지 않는다.
- 변경 범위에 맞는 동작·실패 경로·호환성 검증을 수행한다. 문서·간격 같은 저위험 변경에 불필요한 테스트를 추가하지 않는다. 기존 검증이 충분하면 같은 내용을 중복 검증하지 않는다.
- 가이드 작성, 코드에서의 준수, 시스템 차원의 승인·변경 차단은 별개다. 문서에 원칙을 적었다는 이유로 리팩터링이나 승인 기능이 완료됐다고 보고하지 않는다.

## 하네스 자체 개발의 판단 기준

### 버튼과 아이콘 규칙

- 사용자 결정: 버튼은 SVG 벡터 아이콘을 기본으로 적용한다. 기존 `app/web/static/actions.js`의 공통 아이콘을 재사용하고 크기·선 굵기·정렬을 일관되게 유지한다. 이모지나 문자 기호로 아이콘을 대체하지 않는다.
- 경로 입력 옆 버튼과 폴더 선택·열기 버튼은 폴더 아이콘으로 통일한다. CLI 경로 버튼을 임의로 + 또는 저장 아이콘으로 바꾸지 않는다. 버튼은 입력칸 오른쪽에 간격을 두어 배치한다.
- 닫기는 우측 상단 X 벡터 아이콘, CLI 연결 확인은 안내 문구 옆 연결 아이콘을 사용한다.
- 한글 텍스트가 보이는 버튼은 자동으로 추가하지 않는다. 아이콘만으로 의미 전달이 어려운지, 기존 사용자 합의와 맞는지 검토한 후 적용한다. 기존 텍스트 버튼 전체를 이 규칙만으로 일괄 교체하지 않는다.
- 아이콘 버튼에도 실제 동작을 설명하는 한글 `aria-label`과 툴팁을 제공한다. 아이콘 변경을 파일 선택창 등 새 동작 구현으로 보고하지 않는다.
- 상태 표시는 버튼 아이콘 규칙의 예외로 채워진 원 문자 `●`에 CSS 색상과 상태명을 함께 사용한다. 빨강은 오류, 노랑은 주의·로그인 필요, 녹색은 정상·인증 확인, 파랑은 연결·실행 중, 회색은 미설정·미확인으로 구분한다. 색상만으로 상태를 전달하지 않는다.

- 하네스의 목적은 작업 완료 시간·사람 개입·재작업·토큰 비용을 줄이면서 결과 품질을 유지하거나 높이는 것이다. 기능 수를 성공 기준으로 삼지 않는다. 효과는 비교 가능한 작업과 완료 기준으로 확인하고, 인덱싱·추가 모델 호출·실패 재시도 비용도 포함한다. 측정하지 않은 절감 효과를 보장하지 않는다.
- 사용자 시안이 있는 UI는 배치·영역 책임·상호작용을 요구사항으로 취급한다. 시안을 준비 중인 경우 레이아웃을 임의로 확정하지 않는다. 불명확한 부분은 기존 요구와 비교하고 중요한 차이만 확인한다.
- 하네스 장애가 원본 프로젝트와 네이티브 세션 접근을 막지 않도록 설계한다. 실제 전달 프롬프트·응답·세션 식별자·작업 경로·관련 파일 상태의 기록과 복구 가능성을 검토한다. 비밀정보는 불필요하게 복제하지 않는다. 원본 세션 존재, CLI 재개, 데스크톱 표시, 하네스 상태 복원은 각각 검증하며 하나의 성공으로 나머지를 보장하지 않는다.
- 저장·복구·승인 대기·컨텍스트 선택은 하네스 구현의 책임도 포함한다. 이 가이드의 전달만으로 구현됐다고 간주하지 않는다. 현재 동작은 [실행 계약](client-runtime.md), 후속 구현은 [TODO](TODO.md)에서 확인한다.
